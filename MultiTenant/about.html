About This Demo

This application demonstrates how a multi-tenant Azure Entra ID app registration can authenticate users from any Microsoft 365 tenant or personal Microsoft account using the OAuth 2.0 Authorization Code flow (PKCE) with MSAL.js. While this pattern enables broad reach, it introduces a distinct set of security risks that every organization consuming or hosting a multi-tenant application should understand.

What is a Multi-Tenant Application?

An app registration in Microsoft Entra ID is single-tenant by default — it only accepts sign-ins from users in the directory where it was registered. When the supported account types are set to "Accounts in any organizational directory and personal Microsoft accounts", the app becomes multi-tenant: any user on the Microsoft identity platform can be redirected to consent and sign in. The common authority endpoint handles token issuance across all tenants and personal accounts without further configuration.

This is powerful for SaaS products and public-facing tools, but it also means the application's identity and permission model is visible to — and can be targeted by — anyone on the internet who can construct a valid OAuth request.

Security Risks

🔓
Consent & Permission Abuse

Any user in any tenant can grant delegated permissions to the app, including scopes far broader than your application intends to use. Attackers can craft phishing consent URLs using your legitimate client ID to harvest tokens for sensitive scopes users did not realize they were approving.

🎣
Illicit Consent Grant Attacks

A well-documented Microsoft identity attack pattern: adversaries register look-alike apps that impersonate legitimate services and trick users into granting OAuth consent. Once consent is granted, the attacker obtains a persistent access token with no further authentication, bypassing MFA entirely.

🌐
Tenant Isolation Failures

Multi-tenant apps must validate the tid (tenant ID) and iss (issuer) claims on every incoming token. Applications that skip this validation can inadvertently expose one tenant's data to users from another tenant, or allow cross-tenant privilege escalation.

⚠️
Broad Attack Surface

A single vulnerability — stored XSS, broken object-level access control, or an insecure direct object reference — is exploitable against every tenant that has consented to the application. The blast radius of any security defect scales directly with the number of onboarded tenants.

🔐
Credential & Secret Exposure

Client secrets and certificates used by a multi-tenant app grant access to the identity provider on behalf of all tenants. A single leaked secret or compromised certificate allows an attacker to authenticate as the application to every consented tenant simultaneously.

👤
Privilege Escalation via Guest Accounts

External users invited as guests may receive unintended permissions due to misconfigured role assignments. In a multi-tenant context, a guest in one tenant can use their token to interact with the same application as a user from that tenant if tenant boundary checks are absent or insufficient.

Recommended Mitigations

The risks above are well-understood and addressable through a combination of Entra ID configuration, secure coding practices, and operational controls.

  • Require admin consent. Configure the app registration to require admin consent for all scopes. This prevents individual users from granting delegated permissions and forces an administrator review before any token can be issued to a new tenant.
  • Validate tid and iss token claims. On every API request, verify that the token's issuer and tenant ID match an allowlist of tenants that have been explicitly onboarded. Reject tokens from unexpected tenants rather than trusting the common endpoint blindly.
  • Apply Conditional Access policies. Use Entra ID Conditional Access to enforce compliant devices, approved locations, and strong authentication methods for users accessing the application. Require phishing- resistant MFA (FIDO2 / certificate-based) where supported.
  • Use least-privilege scopes. Request only the minimum permissions required for each feature. Avoid broad scopes such as Mail.ReadWrite or Directory.ReadWrite.All unless absolutely necessary, and audit all granted permissions regularly.
  • Replace client secrets with managed identities or certificates. Avoid long-lived client secrets. Prefer workload identity federation or certificate-based authentication so that no static credential exists that could be leaked from source control or configuration files.
  • Monitor consent grants and sign-in activity. Enable Entra ID audit logs and sign-in logs. Alert on new consent grants, token issuance from unexpected tenants, and application permission changes. Review the OAuth App Governance blade in Microsoft Defender for Cloud Apps for anomalous application behavior.
  • Enforce app-level authorization in addition to token validation. Do not rely solely on scopes granted at consent time. Implement authorization checks within the application layer to ensure that authenticated users can only access resources belonging to their own tenant.
