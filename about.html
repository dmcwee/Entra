About These Demos

This suite of demo applications explores authentication flows, permission models, and common security risks in Microsoft Entra ID. Each demo intentionally surfaces a real-world vulnerability to make the risk concrete and observable.

Client Secret Demo

Demonstrates the OAuth 2.0 Client Credentials Grant — a machine-to-machine flow that authenticates as the application itself rather than a signed-in user. The demo deliberately stores a client secret in browser JavaScript to show that any visitor can extract it from the page source, instantly gaining the ability to acquire application-scoped tokens with no user interaction required.

Key risk: A client secret placed in client-side code is unconditionally compromised — treat it as leaked from the moment of deployment.

Device Code Flow Demo

Demonstrates the OAuth 2.0 Device Authorization Grant (RFC 8628), designed for input-constrained devices. A short code is displayed; the user completes sign-in on a separate device. The demo illustrates how attackers exploit this flow in adversary-in-the-middle phishing campaigns — sending victims a real device code and harvesting the resulting tokens without stealing passwords or bypassing MFA.

Key risk: Device code phishing bypasses MFA because the victim authenticates legitimately; only the resulting token is captured by the attacker.

Multi-Tenant Profile Demo

Demonstrates a multi-tenant MSAL.js application using the Authorization Code flow with PKCE. Unlike a single-tenant registration, a multi-tenant app can accept sign-ins from any Microsoft 365 tenant or personal Microsoft account. The demo highlights risks specific to multi-tenant registrations: guest user access, unconstrained consent, and the ability for any external party to target the application's permission model.

Key risk: Multi-tenant apps are reachable by anyone on the Microsoft identity platform, requiring careful publisher verification, Conditional Access policy design, and admin consent governance.

Mail Sender — Risky Permissions Demo

Demonstrates delegated email sending via Microsoft Graph using the Mail.Send permission — one of the most powerful and most abused delegated permissions in Microsoft 365. Once a user consents, the application can send any message, to any recipient, indefinitely, with no per-message approval. The demo makes the full impact of this permission tangible by actually sending mail on behalf of the signed-in user.

Key risk: Mail.Send is a high-value target for OAuth phishing; a single consent event gives an attacker persistent send-as capability for the life of the refresh token.
