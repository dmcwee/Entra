About This Demo

This application demonstrates the OAuth 2.0 Device Authorization Grant (Device Code Flow) and illustrates why it is one of the most commonly abused authentication flows in modern identity-based attacks.

What is Device Code Flow?

The Device Code Flow (RFC 8628) was designed for input-constrained devices — smart TVs, printers, command-line tools, and IoT devices — that cannot open a browser or accept keyboard input easily. Instead of redirecting the user, the device displays a short code and a URL; the user completes sign-in on a separate device they already trust.

How it Works

  1. The app calls the /oauth2/v2.0/devicecode endpoint and receives a user_code, a device_code, and a verification URL.
  2. The app displays the user_code and URL to the user.
  3. The user visits https://microsoft.com/devicelogin on any browser, enters the code, and signs in.
  4. Meanwhile, the app polls the /oauth2/v2.0/token endpoint every few seconds with the device_code.
  5. Once the user completes sign-in, the next poll returns an access token and optionally a refresh token.

Why It Can Be Risky

The same properties that make Device Code Flow convenient for constrained devices also make it a powerful attack tool. The following threats are well-documented in the wild.

  • Device Code Phishing (T1528). An attacker initiates a real Device Code Flow against your tenant, then sends the user_code and link to a victim via email, Teams, or SMS — disguised as an IT helpdesk request or a routine login prompt. The victim visits the legitimate Microsoft URL, enters the code, and signs in. Because they authenticated against the real Microsoft endpoint, they see no warnings. The attacker's polling loop immediately receives a valid access token and refresh token scoped to the victim's account.
    Why this works at scale The attacker does not need to host a phishing page or intercept any traffic. The entire authentication happens on Microsoft's own infrastructure. The only "malicious" step is sending a 9-character code to the victim — trivially embeddable in any message.
  • No redirect URI to restrict. Authorization Code Flow allows administrators to lock down exactly which URLs a token can be delivered to. Device Code Flow has no redirect URI — any application that holds the correct client_id can initiate the flow and receive a token.
  • Long-lived refresh tokens. On tenants without Continuous Access Evaluation (CAE), refresh tokens issued through Device Code Flow can be valid for up to 90 days. A single successful phish can provide persistent access long after the victim has changed their password (token revocation does not always invalidate already-issued refresh tokens without explicit revocation).
  • No visible app identity at sign-in time. When the user visits microsoft.com/devicelogin, the page shows "Microsoft" — not the name of the specific third-party application that initiated the request. Users rarely question the generic prompt, making it difficult to detect a spoofed or unexpected request.
  • Bypasses MFA assumptions. Because the user completes MFA as part of the Device Code sign-in, the resulting token carries an MFA claim. Downstream controls that rely on "token has MFA" as proof of a secure session cannot distinguish a legitimate MFA completion from one performed unknowingly on behalf of an attacker.

Real-World Threat Landscape

Device Code Phishing has been used in targeted attacks against government agencies, cloud service providers, and enterprise organisations. The technique is documented in MITRE ATT&CK as T1528 (Steal Application Access Token) and has been observed in campaigns attributed to nation-state threat actors exploiting Microsoft 365 and Azure environments.

Mitigations

  • Conditional Access — block or restrict Device Code Flow. Use the Authentication flows condition in Conditional Access to block Device Code Flow entirely, or require a compliant device / trusted location. (authenticationFlowsPolicy in the Microsoft Graph API.)
  • Restrict which applications can use it. Limit the set of approved applications via app-level Conditional Access policies. Require admin pre-approval for any application requesting Device Code Flow.
  • User education. Legitimate IT will never send a user_code via email, Teams, or SMS and ask you to enter it. Any unsolicited device code request should be treated as a phishing attempt.
  • Monitor sign-in logs. Filter Entra sign-in logs for deviceCodeFlow authentication method entries. Alert on codes entered from unexpected IP addresses, countries, or at unusual times.
  • Enable Continuous Access Evaluation (CAE). CAE reduces the effective token lifetime to minutes for supported workloads, limiting the damage window if a token is stolen via Device Code Phishing.
  • Token revocation response. If a Device Code Phish is suspected, immediately revoke all refresh tokens for the affected account in Entra ID (Users > Revoke sessions) and audit the sign-in log for downstream access using the stolen token.
