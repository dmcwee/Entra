About This Demo

This application demonstrates delegated email sending using the Microsoft Graph API and the Mail.Send permission — one of the most powerful and consequently riskiest delegated permissions available in Microsoft 365.

What Does Mail.Send Allow?

Mail.Send is a delegated Microsoft Graph permission that authorizes an application to send email messages as the signed-in user. Once the user consents, the application can send any message, to any recipient, at any time — without asking the user for approval on a per-message basis.

Why Is It Considered Risky?

  • No per-message confirmation. After the user consents once, the app can send unlimited emails on their behalf without any further prompts or approvals.
  • Unrestricted recipients and content. The permission places no limits on who the app can send to, how many emails it sends, or what those emails contain.
  • Token theft risk. A bearer token that carries the Mail.Send scope can be used by anyone who obtains it to send email as the user, for the entire lifetime of the token — typically 60–90 minutes without refresh.
  • Phishing and impersonation. A malicious or compromised application can use this permission to send convincing phishing emails that appear to originate from a trusted user's mailbox.
  • Reputation and compliance exposure. Unauthorized emails sent through a user's account can damage organizational reputation, trigger spam filters, and create compliance liability.

What This Demo Illustrates

This demo shows how little friction exists between an app gaining consent to Mail.Send and being able to act on it. The send action requires only a valid access token — no further confirmation, no secondary approval, and no audit trail beyond what appears in the user's Sent Items folder.

The intent is to help security teams and administrators understand why controls such as admin consent workflows, app permission reviews, and Conditional Access for workload identities are important when Mail.Send is involved.
