About This Demo

This application demonstrates the OAuth 2.0 Client Credentials Grant and illustrates why storing a client secret inside browser JavaScript is one of the most significant secret-exposure risks in modern application development.

What is the Client Credentials Flow?

The Client Credentials Grant (RFC 6749 §4.4) is designed for machine-to-machine (M2M) authentication where no user is involved. The application authenticates as itself — using its own identity — rather than acting on behalf of a signed-in user.

How it Works

  1. The application sends a POST to the tenant's /oauth2/v2.0/token endpoint with its client_id, client_secret, and a scope ending in /.default.
  2. Microsoft Entra validates the credentials and, if the required Application permissions have been admin-consented, returns an access token.
  3. The application attaches the token as a Bearer header on every Microsoft Graph request.
  4. There is no user sign-in prompt, no redirect, and no user session — the token represents the application identity only.

Delegated vs. Application Permissions

The Client Credentials flow exclusively uses Application permissions, not Delegated permissions. Delegated permissions require a signed-in user whose identity is "delegated" to the application. Because this flow has no user, only Application permissions (granted by an administrator via admin consent) apply.

In this demo the app registration must have User.Read.All granted as an Application permission with admin consent. An app-only token with this permission can read every user in the directory regardless of whether any user has consented.

Why Storing a Client Secret in the Browser Is Dangerous

A client secret is functionally a password for the application. Placing it in a JavaScript file that is delivered to every browser exposes it unconditionally.

  • Any visitor can extract it. Opening browser DevTools → Sources or simply viewing the page source reveals the secret in plain text. No special skills or tooling are required.
    This demo intentionally does this for educational purposes. In a real application, a secret in client-side code must be treated as already-compromised from the moment it is deployed.
  • The token has Application-level scope. Unlike a Delegated token (scoped to one user's access), a Client Credentials token carries the full permission set granted to the application. In this demo that means read access to every user in the tenant. An attacker who steals the secret can acquire that same token independently, with no involvement from any user.
  • No user context means no Conditional Access protection. Conditional Access policies that enforce MFA, compliant devices, or trusted locations apply to user sign-ins. Client Credentials tokens bypass all of these controls because there is no user sign-in event. An attacker using a stolen secret from an untrusted network, unknown device, or foreign country will receive a valid token regardless of your Conditional Access posture.
  • Secrets cannot be selectively revoked per client. Rotating the secret (the correct remediation) invalidates it for every instance of the application — including legitimate deployments — forcing a redeployment. If the secret is in client-side code, the old secret is still visible in browser caches, service workers, and CDN edge nodes until they are purged.
  • Browser extensions and XSS can silently exfiltrate it. A malicious browser extension or a single Cross-Site Scripting vulnerability on any page of the application can read the secret from the JavaScript environment and transmit it to an attacker-controlled server.

Recommended Alternatives

  • Backend proxy (strongly recommended). Move token acquisition entirely to a server-side component. The client calls your API; your API acquires the Graph token with the secret stored in a server environment variable or secret store, and proxies only the data the client needs. The secret never reaches the browser.
  • Managed Identity (Azure-hosted workloads). If your application runs on Azure (App Service, Functions, Container Apps, etc.), use a System-assigned or User-assigned Managed Identity. No secret is needed at all — Azure handles credential rotation transparently and the identity cannot be extracted from the environment.
  • Certificate-based authentication. Replace the client secret with an X.509 certificate. The private key can be stored in Azure Key Vault or the Windows Certificate Store, making it significantly harder to exfiltrate than a plain string value.
  • On-behalf-of flow (if a user is present). If a user is already authenticated, use the On-Behalf-Of flow to exchange the user's token for a Graph token scoped to that user's access. This preserves least-privilege and audit trails.
  • Federated identity credentials (workload identity federation). For CI/CD pipelines (GitHub Actions, Azure DevOps) or Kubernetes workloads, use federated credentials to eliminate secrets entirely. The external identity provider (e.g. GitHub OIDC) issues a short-lived token that Entra accepts in exchange for an app token.
